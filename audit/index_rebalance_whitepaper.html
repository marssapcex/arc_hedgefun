Executive summary

What the supplied code appears to permit

The generic public rebalance() path can treat protocol-token input as the fee being checked, while still including the entire input in the reserve invariant calculation. If the selected token weights differ by at most 0.01 ether, the reserve check switches to a constant-product test even though the weights are not equal. The supplied code therefore admits a state transition that reduces the true weighted invariant and can yield positive marked-to-market proceeds under the stated price conditions.

01 · Finding

Near-equal weights are checked as equal; protocol input is counted as fee

The concern is the interaction of two branches in the user-provided Index source—not a claim that ABDKMath64x64 itself is broken.

A. Tolerance selects the wrong invariant

The supplied _ensureReserves() uses an equal-weight product check whenever the absolute weight difference is at most 0.01 ether.

if (
    w1_int > w2_int
        ? w1_int - w2_int <= 0.01 ether
        : w2_int - w1_int <= 0.01 ether
) {
    if (Math.mulDiv(R1_new, R2_new, R2_original) < R1_original) {
        revert Index__SameWeightReservesViolation();
    }
} else {
    // weighted logarithmic invariant check
}

Factory permits weights 2.50 and 2.51; their difference is exactly the inclusive threshold. Their relative difference is 0.4%, so they are not mathematically equal.

B. Generic fee check can reuse the input

In generic rebalance(), the reported fee is the increase in the protocol-token balance. If protocol token is also tokenIn, that increase is the trade input itself.

uint256 fee = getBalance(tokens[0]) - balanceProtocolToken;
uint256 minFee =
    (deltaIn * balanceProtocolToken
        * getCurrentWeight(_tokenIn) * swapFee())
    / (balanceInBefore
        * getCurrentWeight(tokens[0])
        * (1000 + swapFee()));

if (fee < minFee) revert Index__InsufficientFee();

The generic path then checks reserves using full balanceIn. Unlike rebalanceProtocolTokenIn(), it does not subtract the calculated fee from input before applying the invariant.

Access conditions: the attacker needs an unlocked target pool, a compatible weight pair, liquidity, and a means to realize the output value. The caller supplies the callback contract; no owner/admin call is part of the described path. A pool owner can lock rebalancing, so a locked pool is not exposed while the lock is active.
02 · Mathematical argument

Why the product check can pass while weighted K falls

Let protocol/input weight be a, output weight be b=a+δ, with reserves P and O. The true normalized weighted invariant is:

ln K = (a ln P + b ln O + Σj≠pair wj ln Rj) / W,   W = 50 ether

With input x, the largest integer output used in the regression is y = O − ceil(P·O/(P+x)). Ignoring the sub-unit floor margin for the real-valued derivation, the equal-product boundary satisfies:

(P + x)(O − y) = P·O
ln((P + x)/P) + ln((O − y)/O) = 0

The true weighted change on the pair is therefore:

Δ ln K = [a ln(1 + x/P) + b ln(1 − y/O)] / W
≈ [(a − b) ln(1 + x/P)] / W
= [−δ ln(1 + x/P)] / W < 0   when δ > 0

The actual code uses integer Math.mulDiv and floors. The regression selects an output for which the exact integer condition passes; the independent high-precision model then measures the weighted-log change. The concrete case decreases normalized ln K by approximately 3.9960 × 10⁻⁷.

Fee algebra when tokenIn is protocol token

Assume reserve accounting has reserve = 0, so balanceInBefore = balanceProtocolBefore = P, and weightIn = weightProtocol = a. For input x and swap fee f:

fee measured by generic rebalance = Δ protocol balance = x
minFee = floor(x · P · a · f / (P · a · (1000 + f)))
      = floor(x · f / (1000 + f))
⇒ measured fee x ≥ minFee, but the invariant still sees the full input x.

This derives directly from the supplied expression. The numeric check alone is not evidence of loss; the critical fact is that full input remains in the invariant calculation while the equal-weight approximation accepts a weighted-invariant decrease.

Upper-bound analysis

Best-case extraction fraction

For equal starting reserves and price ratio b/a, the constant-product output has marked profit:

profit/P = z(q−z)/(1+z)
q = δ/a; z = x/P
z* = √(1+q)−1
max profit/P = (√(1+q)−1)²

With the most permissive pair a=2.50, δ=0.01, the theoretical maximum is about 3.992 × 10⁻⁶ of protocol-side reserve value, before liquidation costs. This is bounded arbitrage, not a full-pool drain.

Why no reliable total-loss number is available

Protocol TVL includes multiple products/positions and may include index-token valuations. The bug only applies to pools whose live weights, token balances, fee state, reserve accounting and exit liquidity meet the required conditions. A screenshot of total TVL cannot establish those facts.

Applying the theoretical factor to all $273,140 would give roughly $1.09, but that is only an intentionally overbroad arithmetic ceiling if every dollar were eligible protocol-side reserve. It is not a verified impact estimate or bounty valuation; actual exposure could be lower or zero for a pool without the required configuration/market.

Flashloan interpretation: a zero lender fee removes a capital constraint, not the exit-market cost. The local test models 10 bps at the separate liquidation venue. Actual market depth, route fees, price impact, token behavior and same-Vault reentrancy restrictions must be measured on an authorized fork before estimating net extractable value.
06 · False-positive analysis & confidence

Why the math is concerning—and why deployment confirmation still matters

Evidence against a mere rounding alarm

  • The threshold comparison is inclusive; a gap exactly equal to 0.01 ether enters the equal-weight branch.
  • The Factory constraints allow the illustrative weights and total weight.
  • The fee algebra simplifies exactly for tokenIn == protocolToken; it is not a floating-point approximation.
  • The chosen output satisfies the exact integer product-floor predicate.
  • The weighted-log loss is independent of ABDKMath64x64 because the test enters the product branch.
  • The reduced EVM test executes callback transfers, fee check, and lender repayment; arithmetic fuzz independently checks profitability and invariant direction.

Remaining uncertainty / possible disconfirmation

  • No full `Index` source file was present in the repository checkout; the EVM harness is reduced, not the deployed contract.
  • No archive RPC or mainnet fork was used; deployed factory/index bytecode and current pool states remain unchecked.
  • No actual external market was queried; marked profit depends on a price consistent with the stated weighted marginal price and sufficient exit liquidity.
  • The screenshots do not prove that any live pool currently has the test weights, balances, unlocked state, or fee conditions.
Conclusion: strong source-level mathematical evidence for the supplied snippet; deployed exploitability and bounty-sized impact remain unconfirmed. This must not be submitted as a fork PoC until the exact deployed implementation passes an authorized fork test.
07 · Remediation

Recommended changes

  1. Do not substitute a different invariant based on an absolute tolerance. Always check the actual weighted invariant, or use a rigorously bounded conservative approximation that cannot accept a decrease.
  2. Prevent fee/input aliasing. In generic rebalance(), reject protocol-token input/output and require callers to use the dedicated protocol-token functions, or compute and subtract the fee from effective input before invariant validation.
  3. Round in the pool’s favor. Use conservative output/input rounding and test one-wei and extreme-ratio states; avoid relying only on a fee inequality that can be satisfied by the swap input itself.
  4. Add stateful invariant fuzzing. Fuzz sequences over all token pairs, transitions, reserves, fee states and protocol-token directions. Assert weighted K never decreases after fees and accounting are applied.
  5. Validate on an authorized fork before closing. Pin a block, verify implementation/source hashes, choose a real affected pool, and have the protocol reproduce the finding with a non-broadcast test transaction.
